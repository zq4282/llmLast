# 业务查询插件设计草稿

状态：业务边界已确认，第一版已实现。真实订单接口及固定时效数值仍需业务提供；当前读取项目演示订单，未配置的具体时效提示由人工确认。

## 1. 已确定的业务边界

三个场景统一进入 BUSINESS_QA 对应的 business_inquiry 插件：

- 场景 1：扣费质疑与账单核查。
- 场景 5：二次来电催问退款进度。
- 场景 7：线下扫码混淆与错打热线。

用户确定的服务路径：查询用户订单状态，简单解释订购路径，说明立即协助处理的安排及固定时效，附带道歉安抚，再次询问用户诉求。明确无诉求则结束；需要继续处理则转人工。

已确认约束：

1. “立即处理”指转人工处理，本插件不执行退款、退订或催办。
2. 订单信息由业务配合提供，目标是包含场景所需信息；接口未返回的信息不得推测。
3. “继续跟进”指转人工，不在本服务内建立人工工单或跟踪流程。
4. 第一版使用固定时效，按场景独立配置；具体数值及含义由业务提供，不擅自填写。
5. 返回 HUMAN 即结束当前机器人流程。其他程序接管后续处理，与本服务无关。

机器人查询接口仍有责任区分成功、无记录和异常；真实转接和人工处理不在本文范围内。

## 2. 架构与维护边界

采用“一个公共流程，三个独立场景模块”。共用状态机制和查询协议；场景专属判断、解释、安抚和时效各自保存。

| 部分 | 职责 | 修改边界 |
| --- | --- | --- |
| 现有引擎 | 路由、动作执行、回复渲染、会话生命周期 | 不增加扣费、扫码等场景分支 |
| 查询插件公共流程 | 查询信息收集、订单选择、等待诉求、结束 | 修改后验证三个场景 |
| 场景模块 | 所需信息、事实整理、场景提示、固定时效、话术 | 只能影响本场景 |
| 查询服务 | 提供订单及相关记录，区分结果类型 | 协议保持兼容，变更做调用方回归 |
| 外部人工服务 | HUMAN 之后的处理 | 不属于本服务 |

场景模块之间不互相调用或读取对方配置。公共模块不保存某个场景的专属解释或时效。不能保证公共代码修改绝不影响调用方，通过限制依赖、稳定协议和回归验证控制影响。

第一版目录：

```text
app/businesses/business_inquiry/
  plugin.yaml                 # 公共状态、转移及恢复规则
  prompt.md                   # 公共意图，仅注入当前场景规则
  handlers.py                 # 引擎动作入口
  scenario_registry.py        # 显式登记场景
  scenarios/
    charge_dispute/
      config.yaml             # 查询要求、固定时效及适用含义
      prompt.md
      replies.yaml
    refund_progress/
      config.yaml
      prompt.md
      replies.yaml
    scan_confusion/
      config.yaml
      prompt.md
      replies.yaml
```

目录由查询插件内部读取，不要求引擎原生支持一种新插件类型。第一版只做简单登记和三个具体模块，不建设通用场景编排平台。当前场景差异全部由配置表达，事实字段约定及校验放在 scenario_registry.py，不创建无实际用途的场景代码文件。

## 3. 公共流程与结束语义

正常流程：

```text
进入业务查询
  → 定位并查询订单
  → 解释记录、说明人工处理安排与固定时效、道歉安抚
  → 询问是否还有需要处理的诉求
      → 明确需要处理：HUMAN，结束当前机器人流程
      → 明确没有诉求：END，结束当前机器人流程
      → 回复含糊：澄清是否需要处理
```

说明安排时可以说“如需进一步处理，我马上为您转人工”；决定转人工并返回 HUMAN 时再说“正在为您转接人工”。不能先返回 HUMAN，再等待用户回答。

用户已明确要求人工或进一步办理时，直接转人工；已有可用查询结果可简述后转接，不重复询问诉求。主动要求人工不以查询成功为前提。

建议状态：

| 状态 | 含义 | 走法 |
| --- | --- | --- |
| IDLE | 首次进入 | 查询成功后回复并进入 WAIT_REQUEST；缺信息或多订单走对应状态 |
| ASK_ORDER_INFO | 缺少信息或初次无记录 | 补充定位信息后再查；无法提供或要求处理则人工 |
| RETRY_ORDER_INFO | 补充后仍未定位 | 最后核对一次，仍失败则人工 |
| SELECT_ORDER | 多笔候选 | 根据用户选择确认订单；无法确认则人工 |
| WAIT_REQUEST | 已解释并询问诉求 | 有需处理诉求则人工，无诉求则结束，含糊则澄清 |
| END | 本服务处理结束 | 不继续调用查询或业务动作 |

查询和澄清返回 CHAT。转人工返回 HUMAN；明确结束返回 END。HUMAN 与 END 均终止当前活动流程，遵循现有会话机制，不删除历史记录。后续若仍向同一 sessionId 发新请求，现有引擎可重新路由；这不代表本服务跟踪人工处理。

“嗯”“知道了”不自动判定无诉求。用户继续质疑、继续追问、要求退款或退订，都视为仍有诉求，转人工；不在 WAIT_REQUEST 中循环解释或进入其他办理插件。

查询异常按人工兜底处理，不能说查无订单，也不能要求用户反复换号码。有限核对次数复用项目已有规则。

## 4. 三个独立场景

| 场景 | 查询后的事实说明 | 固定时效及特殊规则 |
| --- | --- | --- |
| charge_dispute | 产品、扣款金额、支付状态、订购时间和渠道 | 单独配置人工处理安排和时效；否认订购或不认可解释则人工 |
| refund_progress | 产品和订购路径简述、退款状态、退款渠道、申请及处理时间 | 单独配置时效；已超出时效或退款失败如实说明并转人工，不重置等待时间，不再次提交退款 |
| scan_confusion | 产品、订购渠道，以及实际存在的扫码关联记录 | 单独配置核查处理时效；无关联证据不推断扫码导致订购，也不因本系统无订单就认定错打热线 |

业务应为每个场景提供：查询字段说明、状态对应解释、订购渠道说明、固定时效的数值及适用含义、正常与异常话术。

固定时效必须明确指人工处理、退款到账还是其他对象，三个场景不共用一个模糊的“几天内处理”。时效暂未配置时使用“具体处理时效需要人工进一步确认”，不填写虚构值。

查询到的记录来自接口；用户声称来自对话。二者分开保存。用户说“前天答应退款”不能直接变成“已提交退款”的事实。已查到退款申请可以说明其状态，但本插件不能声称自己已提交退款或催办。

三个场景各自保存完整业务话术，不继承会同时改变三个场景的一段长模板。通用字段格式化可以共用。

## 5. 查询与上下文隔离

现有 app/services/order_lookup.py 按办理条件筛选支付成功、未退款或订阅中的订单，手机号查询取最新一笔。核查插件不能直接采用该查询语义。

第一版保留旧服务行为，新增核查查询入口，支持已退款、退款失败等记录及多笔候选；可以复用底层接口访问。不能因增加核查场景改变退款、退订插件原有筛选行为。

查询结果区分：缺少条件、没有记录、多笔候选、接口异常、订单存在但部分事实缺失。缺少订购渠道或退款详情不是查无订单，不要求用户重新提供手机号，可说明后转人工。

建议 context 分区：

- inquiry_meta：场景 ID、当前问题、用户诉求、定位信息。
- verified_order：接口返回的已定位目标订单事实。
- scenario_data：当前场景退款详情或渠道记录。

场景模块只能使用约定事实整理自己的 scenario_data，不能覆盖 business、plugin_state、out 等引擎字段，由公共 handler 适配现有 ActionResult。

当前引擎动作失败不会保存失败查询的上下文。查询未成功时，原问题保留在对话历史中；下一轮识别必须根据历史补充 scenario_id。多笔候选只展示，不保存为已确认事实；用户选择后提供明确订单号重新查询。

换订单时清除相关旧场景数据；同一订单换场景时可复用定位信息，但新场景数据重新初始化，易变状态重新查询。用户在等待诉求阶段提出新的处理问题则直接人工，不额外切换场景继续解释。

第一版无需新增查询到退款、退订插件的上下文交接机制。现有直接退款、退订入口及办理插件继续保留，本次不改变它们的业务行为。

## 6. 修改范围与验收

| 改动 | 必须验证 |
| --- | --- |
| 单场景提示、话术或时效 | 本场景对话与配置；其他场景输出隔离 |
| 公共流程或场景协议 | 三个场景完整回归 |
| 查询服务、顶层路由或引擎 | 三场景及现有退款、退订、组合办理、人工、other 回归 |

场景配置显式登记并校验 ID、字段、话术引用。缺失场景配置明确报错，不借用别的场景配置。数据协议新增字段保持兼容；改名、删除或改变语义必须兼容处理。

日志记录流程 ID、场景、订单定位、查询结果类型及结束原因，不记录本服务无法感知的人工处理状态。

第一版验收：

1. 三个典型入口进入正确场景；退款进度询问不会进入新退款办理。
2. 三场景均覆盖查询成功、信息不足、多候选、无记录和接口异常。
3. 查询成功后按服务路径解释安抚、说明安排和时效、询问诉求。
4. 有后续诉求返回 HUMAN；无诉求返回 END；含糊回复有限澄清，最终按已有恢复规则人工兜底。
5. HUMAN 后结束当前流程，无再次查询、退款、退订、催办或人工跟踪动作。
6. 修改一个场景规则不会改变其他场景的配置及行为预期。
7. 切换目标订单不串用旧订单事实；退款时效不会每次查询重新计算起点。
8. 现有插件和会话生命周期测试保持通过。

使用固定查询结果与固定意图结果验证流程和隔离，另做少量模型对话评估识别效果。只有后续提出了新的独立业务目标，才考虑新增插件。

实施前剩余业务输入：真实查询接口契约、三场景说明话术与固定时效。流程设计不再需要扩展人工接管后的责任。
